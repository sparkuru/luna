# Deployment and Recovery Contract

## 1. Scope / Trigger

Apply when editing Dockerfiles, Compose, Nginx, server startup/admin commands,
runtime secrets or recovery tooling. The current production boundary is one
`compose.yaml` with Web, API, server SQLite metadata and the pinned internal
MinIO object store. Validate the exact Docker/Compose version on the target;
the deployment must remain usable with the oldest supported Compose binary.

## 2. Signatures

```text
docker compose up --build -d
docker compose exec api node dist/server/server/cli/admin.js create-account
docker compose exec api node dist/server/server/cli/admin.js reset-password
docker compose exec api node dist/server/server/cli/admin.js cleanup
```

`instance-init` creates `data/.luna/minio.env` and the `initialized` marker;
`bucket-init` runs after MinIO starts, creates `luna-sync`, installs a restricted
service access key, and writes `data/.luna/runtime.json` and
`bucket-initialized` as separate atomic files. Both steps reuse valid existing
state. The normal path needs no host Node toolchain, pre-created secret files,
or shell script. Admin account commands require an interactive terminal and
hidden password confirmation.

Use an explicit project name (`docker compose -p <name>` or
`docker-compose -p <name>`) instead of relying on a root-level Compose `name:`
field; the latter is rejected by Compose 1.29.x. The root Docker build context
must keep the server allowlist entries for `Dockerfile.server`,
`Dockerfile.bucket-init`, `deploy/bucket-init.mjs`, `tsconfig.server.json`,
`src/server/**`, and `deploy/server-runtime-package.mjs`, because the classic
builder applies the root `.dockerignore` even when a Dockerfile-specific ignore
file exists.

Compose inputs are `LUNA_BIND_HOST`, `LUNA_PORT`, `LUNA_ALLOWED_ORIGINS`,
`LUNA_ALLOW_INSECURE_LAN`, and optional `LUNA_UID`/`LUNA_GID` for the
bind-mounted `data/` owner. API's internal port is fixed at 3000. The API reads
`data/.luna/runtime.json`; its S3 contents never enter a client response. The
root MinIO credentials are generated by `instance-init` and reused on restart;
separate API credentials are generated by `bucket-init` and reused on restart.
`LUNA_ALLOW_INSECURE_LAN=true` is a deliberate trusted-RFC1918-IPv4
HTTP exception; HTTPS remains required for production or untrusted networks.

## 3. Contracts

- Only Web publishes a host port, loopback by default. API and MinIO remain on
  Compose's private network; public or cross-device use requires a trusted
  HTTPS reverse proxy and a reachable hostname/IP.
- `data/` contains `.luna/runtime.json`, `.luna/minio.env`, the initialization
  marker, `server.sqlite` and its WAL/SHM sidecars, and the MinIO object tree.
  It is the server backup boundary. Do not describe a container layer or a
  single SQLite file as the complete shared ledger backup.
- `minio.env` holds only the MinIO root pair (0600); MinIO reads it through
  `MINIO_CONFIG_ENV_FILE`, so Compose and Docker inspect do not contain root
  values. `runtime.json` holds a different access key with `s3:ListBucket` on
  `luna-sync` and `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` only on
  `luna-sync/luna/*`. `bucket-init` checks its policy and key on repeat start.
  An old runtime equal to the root pair is upgraded in place. If creation
  succeeded but writing `runtime.json` was interrupted, the next bootstrap
  removes unreferenced `luna-sync-api` keys with the expected policy before
  issuing a replacement. A missing bucket on an installation with an existing
  runtime fails; it is never silently recreated as empty.
- API's `/data/.luna/minio.env` mount is an empty file and `/data/minio` is an
  unreadable tmpfs. These mounts hide root material and object files despite
  API's writable bind mount for `server.sqlite`. Keep them when changing
  Compose.
- The server SQLite schema stores users, sessions, account-ledger ownership,
  object metadata, idempotency records and sanitized security events. It does
  not store financial plaintext. MinIO stores client-encrypted envelope bytes.
- Server schema v3 also stores exact attachment orphan generations. Expired or
  canceled reservation tokens are fenced before their physical keys enter the
  delayed reconcile queue; `admin cleanup` must run that queue against the
  configured File/S3 object store. Orphan tombstones remain after a successful
  delete so a late upload of the same old generation cannot survive the next
  sweep or affect a newer published key.
- API writes use one in-process writer mutex around authorization, CAS,
  object-store operation and metadata update. The single-instance deployment
  must not be scaled horizontally without a shared locking/transaction design.
- API startup migrates/validates SQLite, waits for MinIO with a bounded retry,
  and only then listens. Health is liveness; readiness also proves schema and
  object-store availability. Failure is visible and never creates an empty
  replacement database.
- The Web image healthcheck probes `127.0.0.1` only after clearing inherited
  HTTP proxy variables; a host-injected proxy must not turn a local Nginx
  healthcheck into a false 502/unhealthy result. MinIO keeps the same runtime
  boundary as the other services: non-root UID/GID, read-only rootfs,
  `cap_drop: ALL`, `no-new-privileges`, a bounded writable `/tmp` tmpfs, and
  the persistent `data/` bind mount.
- The API runtime contains only compiled server code and the runtime roots
  `fastify`, `@fastify/swagger`, `better-sqlite3`, and `@aws-sdk/client-s3`.
  Web/Android clients receive authenticated API access, never S3 credentials.
- Nginx applies `no-store, no-transform` to `/api`, streams requests, preserves Authorization,
  ETag, conditional and idempotency headers, and uses bounded Docker DNS
  re-resolution for API replacement. Unknown API paths and missing assets do
  not receive the application shell.
- Web responses include COOP `same-origin` and COEP `require-corp`, allowing the
  browser client to use the regular multi-tab OPFS VFS. The embedded Android
  client uses SQLite-WASM's `opfs-sahpool` path and does not depend on these
  response headers. Cross-device HTTPS must still preserve them for Web.
- The Web CSP keeps ordinary JavaScript `unsafe-eval` disabled but includes
  `wasm-unsafe-eval`, which is required for the SQLite-WASM module to compile;
  removing it makes every browser ledger open fail as a generic storage error.
- Limits match Fastify: sessions 2 KiB, ledger creation 1 KiB, preferences
  1 MiB and encrypted ledger 12 MiB. Forwarded client IP is not trusted; this
  is a one-instance small-installation rate-limit contract.
- Restore always starts in a new directory/project. Preserve the instance ID,
  account state, object metadata, ETags and exact ciphertext before switching
  traffic. Clients refetch and merge after restore; they never blind-upload an
  old snapshot.

## 4. Validation / Error Matrix

| Condition | Required outcome |
|---|---|
| Empty data directory | `instance-init` creates root file/marker; `bucket-init` creates bucket and limited runtime before API starts |
| Existing initialized data | Root/API credentials and instance identity are reused byte-for-byte; an unexpected access-key policy fails |
| Legacy runtime equals MinIO root | `bucket-init` installs a separate limited key without clearing objects or changing root |
| Existing runtime but MinIO bucket missing | `bucket-init` fails before API starts; do not create an empty replacement bucket |
| Partial `.luna/`, missing runtime after `bucket-initialized`, existing SQLite without runtime, or invalid future schema | Initialization/API fails without clearing data |
| Wrong data ownership/permissions | Container fails visibly; no empty replacement is created |
| MinIO unavailable | API remains unready and retries are bounded |
| Compose v1 parses the project | No root-level `name:` field; use explicit `-p` |
| Classic builder misses server files | Root `.dockerignore` allowlist includes every server build input |
| Web healthcheck returns proxy 502 | Probe loopback with all HTTP proxy variables unset |
| MinIO read-only rootfs cannot start | Provide only bounded `/tmp` tmpfs and persistent `/data` write access |
| SQLite stopped/corrupt | Liveness/readiness and sanitized API errors are distinct |
| Missing JS or unknown API | 404, no application shell |
| API success/error/proxy error | `Cache-Control: no-store, no-transform` |
| Oversized route request | 413 before application state changes |
| Restored object and stale CAS | 412; client re-downloads, merges and retries conditionally |
| Backup while writes are active | Not accepted as a plain file copy; use a stop window or consistent snapshot |

## 5. Good / Base / Bad Cases

Good: preserve source directory prefixes while staging, run the explicit project
name through the target's actual Compose binary, build with the root allowlist,
then stop API and MinIO, copy the complete `data/` tree with numeric IDs,
restore it into a new Compose project, verify `/api/v1/meta`, login, decryption,
and two-device merge, then switch traffic.

Base: an empty directory runs two ordered, idempotent initializers and an admin
explicitly creates the first account.

Bad: flattening `src/` or `deploy/` during staging, copying only
`server.sqlite`, copying a live WAL/object tree with `cp -r`, deleting
`.luna/initialized` to reset a deployment, exposing MinIO ports, weakening the
MinIO sandbox for a healthcheck, exposing the root file/object mount to API,
or running `down -v` against an existing installation.

## 6. Tests Required

Run `docker compose config` (and the target's `docker-compose config` when
Compose v1 is in scope), `./hako npm run server:build`, `./hako npm run
web:build`, server tests, and the isolated Compose backup/restore smoke when
Docker images are available. The deployment smoke must assert successful API
and Web image builds under the target builder, healthy Web status despite the
host proxy environment, MinIO's read-only/capability boundary, loopback-only
publishing, stable instance identity, and API-level object readability after
restart. The full smoke must use disposable labeled resources, copy the entire
`data/` boundary, verify stable instance identity and exact ciphertext/ETag,
exercise stale CAS and idempotency, and validate Nginx route and security
headers. It must never touch a user's existing Compose project.
For the two-stage bootstrap, assert root and API keys differ, exact runtime
bytes survive a second start and stopped-copy restore, API cannot read
`minio.env` or list `/data/minio`, the limited key receives 403 for bucket
creation and writes outside `luna/`, and a synthetic old root runtime upgrades
without changing root credentials. Simulate interruption after key creation:
the old key must return 403 after the next bootstrap. Include
`Dockerfile.bucket-init`, `deploy/bucket-init.mjs`, and `.dockerignore` in
recovery staging so restored `data/` secrets are not sent into the Docker build
context.
Delete the bucket only in a disposable installation and assert a subsequent
bootstrap fails while preserving `runtime.json`.

Human acceptance additionally checks real hostname routing, HTTPS certificate
trust on a second browser and Android device, cold/offline local SQLite reopen,
manual-mode unsynced records, and restoration from an off-host copy. A browser
loopback fixture is not evidence for these boundaries.

## 7. Wrong vs Correct

Wrong: require users to create `postgres-password` files, expose MinIO keys in
the device UI, let API use MinIO root or read its root file, or call a health
endpoint “ready” while the object store is not available.

Correct: `docker compose up --build -d` initializes one private `data/` folder;
the API uses only a restricted internal S3 key, clients authenticate to the API, and
readiness is withheld until both SQLite metadata and MinIO are usable.
