# Research: encrypted transaction images across local storage, backup and sync

- Query: Can approved image attachments be delivered coherently on existing Luna clients and transports?
- Scope: internal; source-backed architecture recommendation, not implemented behavior
- Date: 2026-09-12

### Recommended architecture (single direction)

**Graph v2 holds immutable image descriptors; image ciphertext lives in separately addressed immutable blobs. Full backup packages the encrypted graph plus every referenced ciphertext blob. Preserve one authoritative CAS graph head.**

1. Add ordered `attachments` to transaction values, maximum 9. Descriptor contains random opaque attachment ID, workspace ID, image MIME, pixel dimensions, normalized byte length, ciphertext length and SHA-256, cipher version, random AES-256 key and IV. Key/MIME/dimensions remain inside the encrypted graph remotely; never expose keys in renderer snapshot/list APIs, URLs, logs or server metadata. Random immutable ID refers to exactly one ciphertext/digest; collision with different bytes rejects. No global cross-profile plaintext hash deduplication.
2. Decode/re-encode JPEG/PNG/WebP still images into a supported normalized still format; strip EXIF/GPS and original filename. Reject unsupported/animated images with a recoverable message. Recommended admission bounds: source <=20 MiB and <=40 megapixels, normalized long edge <=2048 pixels, <=2 MiB per image, <=9 images per transaction. These are chosen product limits, not existing values or device-tested performance claims. Pixel limit must be checked from bounded headers before large decode; do not rely solely on file extension/MIME.
3. Generate one random image key and IV per immutable normalized image. AES-GCM authenticates a canonical domain-separated header containing protocol version, workspace/attachment IDs and plaintext byte length; descriptor authenticates ciphertext digest/size through the encrypted graph. Encrypt once and persist exact ciphertext for idempotent retries. New image/replacement means new ID/key/IV, never nonce reuse. Offline local save requires neither login nor sync passphrase: per-image keys live with local graph under the existing local DB security boundary. This does **not** add whole-device at-rest protection; remote graph encryption protects the keys in transport/backup.
4. Main/worker host owns image encryption and blob persistence; renderer gets bounded preview bytes or object URLs and opaque draft tokens only. Revoke URLs on close/profile change, do not cache decrypted images in service worker. Preprocessing remains outside database write locks. Draft tokens are bound to profile/workspace and captured edit version.
   **Required public API correction:** `src/shared/api.ts:32`–`:34`, `src/preload.ts:51`–`:54` and `src/main/ipc.ts:63`–`:67` currently expose raw graph reads/merges and full conflict values. With keys in descriptors this would leak keys. Move raw graph methods to host-internal `LedgerDataPort` and remove their renderer IPC exposure; replace conflict return values with a key-free DTO preserving IDs/heads/visible financial fields and safe attachment metadata. Keep host-side selection by head ID for resolution. Project `Transaction` snapshots/create/update receipts similarly; do not solve this merely by asking components not to read secret fields. Existing renderer tools use conflict reads (`src/renderer/features/tools.tsx:41`), so update that consumer and test projections recursively. Web's worker is a correctness/ownership boundary, not protection against a fully compromised same-origin application; do not claim XSS-proof local key storage.
5. Local save uses a single transaction to validate expected transaction revision, attach verified staged ciphertext records, append graph revision and update projection/pending state. Failure leaves the draft and previous committed financial state intact. A successful receipt prevents replay if UI refresh subsequently fails. Staging rows may exist before save but are not visible ledger state; garbage-collect only abandoned unreferenced draft staging after the owning session closes/expires, never committed history. Profile switching freezes/drains accepted operations and cancels previews/staging access just as existing host transitions do.

### Limits, completeness, retention

- Proposed default logical ciphertext inventory budget is 512 MiB per local profile/remote ledger, including retained historical images and durable upload reservations. Count unique attachment IDs, not each revision reference. This is an admission ceiling, not guaranteed device capacity: estimate available browser storage, then handle real quota failures atomically. Provide used/capacity information and a precise quota error. Account-wide/operator budgets must also prevent unlimited ledger creation from bypassing capacity; expose server-advertised limits instead of claiming all servers allow 512 MiB.
- Removed/deleted images and losing conflict candidates remain reachable from revision history and **must be retained**. No automatic GC of committed attachment blobs in this release. Visible remove means remove from current transaction, not erase historical bytes; explain this when relevant. Full backup includes every unique descriptor referenced by **all graph revisions**, including tombstones and conflicts.
- No retention grace period is safe proof that an offline client no longer needs a blob. Remote deletion/graph compaction is a separate future protocol requiring causal retention rules. Unpublished remote orphan uploads consume quota; do not silently claim automatic reclamation. Begin with bounded reservations/inventory and explicit operator/account retention policy; failed upload retry reuses its ID. Quota exhaustion never deletes financial data or automatically strips an attachment.
- Distinguish financial graph synchronized, attachments pending/unavailable, and fully synchronized. Fetch missing blobs with bounded concurrency (initially 2) and per-object timeouts; retry by immutable ID/digest. Missing bytes must not change monetary totals or turn a valid transaction into financial conflict. Details show recoverable image-unavailable state. Never report full backup/sync completion with missing or corrupt images.

### Sync protocol and server mechanics

1. Capability-check account server before v2 upgrade/remote activation: supported graph/envelope/attachment versions, per-image and aggregate limits. Old server or mismatched feature set produces upgrade-required while local bookkeeping stays available; do not silently send graph-only data.
2. Continue using the existing authoritative head key `ledger-v1.enc.json` for legacy S3 (name is historical; envelope announces v2), and existing account ledger object route. **Do not create a second writable `ledger-v2` head**. New client reads v1 and v2; old clients fail on v2 before writing. CAS makes an old client's pre-upgrade ETag stale. Account server persists minimum accepted payload version and rejects downgrade PUT, even with a fresh ETag.
3. Add authenticated account attachment PUT/GET routes scoped by existing ledger authorization and opaque image ID; PUT is immutable/create-only with bounded ciphertext body, expected digest, bounded size and idempotency. Existing ID+same digest is success, different bytes is conflict. No public image URL, plaintext metadata, direct server S3 credential or guessed cross-ledger lookup. S3 adapter implements equivalent objects under the same normalized ledger prefix in `attachments/v1/<id>`; both adapters obey one shared attachment port.
4. Server attachment metadata/inventory includes owning ledger, object key, ciphertext digest/length, upload state and quota reservation. Reserve capacity transactionally before upload; write immutable blob; verify; finalize inventory. Crash/retry reconciles the same reservation+ID and cannot charge twice. Do not hold a global SQLite write transaction across a long image upload. Enforce bytes while streaming; declared Content-Length is not sufficient. Add bounded staging lifetime and recovery reconciliation for incomplete uploads; completed unpublished blobs remain accounted for until a deliberate future retention rule.
5. Graph sync reads/decrypts remote head, validates/merges locally against current state, resolves descriptor collisions, inventories all revision references. Upload locally available required images before publishing a graph that first references them. Verify remote presence/digest for preexisting references. On missing remote image retain financial graph but expose attachment-incomplete, avoid successful full-sync acknowledgement; support repairing from a device possessing bytes.
6. Download and authenticate missing remote images to staged profile storage; promoting each valid blob is atomic. Publishing a graph does not require downloading every historical image first, but full sync does require the graph and required image inventory be complete. CAS conflict reruns merge and inventories the new union; never upload a stale replacement graph or re-encrypt immutable images. Before reporting fully synced compare latest local graph plus attachment completion, not only JSON equality.
7. Disconnect/revoke/profile switch cancels transfers and checks profile generation at commit boundaries. A late operation cannot populate a different account's database. Independent local save remains usable while image transfers are pending. Existing manual/automatic mode semantics apply to attachments too.
8. Update HTTP schemas/OpenAPI/SDK generation, validators, CORS/content types, admission/rate limits, S3 fixtures, Docker/server backup inventory and restore verification together. Server infrastructure backups must cover new attachment inventory and physical objects, not just the legacy single graph object. Do not modify or overwrite unrelated generated SDK fixes during planning.

### Full backup format and restore

- Keep legacy encrypted JSON import. Introduce a versioned binary framed full-backup format, not base64 images in a giant JSON string and not a new unreviewed ZIP dependency. Export header/version, encrypted manifest, length-prefixed bounded encrypted records and completion footer. Freeze a canonical graph snapshot and its unique attachment inventory for export; subsequent local edits belong to the next backup.
- Manifest contains the graph and ordered unique attachment IDs, ciphertext digests and lengths and expected record count/total. Encrypt the manifest with the existing password KDF/AES-GCM parameters using a **new backup format domain/AAD**; image ciphertext stays separately encrypted under keys inside manifest graph. Graph/manifest remains bounded (initial suggested 16 MiB plaintext, 24 MiB encrypted; exact inventory overhead must be calculated against existing 8 MiB graph and <=10,000 revisions); entire container bound 544 MiB for proposed 512 MiB blobs plus manifest/framing. Authenticate expected lengths/digests/order via manifest; reject truncation, duplicates, extras, unsupported versions and footer mismatch before commit.
- Export/import are streaming/chunked through a host-owned backup port. Per-chunk bridge budget <=1 MiB, one chunk outstanding, progress/cancel; never pass 512 MiB through one IPC/Capacitor string. Web may build a disk-backed staged export and return a download Blob where necessary, but must prove bounded working memory; unsupported runtime is explicit, not fake success. Native Android needs SAF begin/write/finalize/cancel and matching read/restore path; Electron uses user-selected file handles without exposing paths. Current legacy text export remains for v1 compatibility, never silently omits attachments.
- Import validates bounds/password/manifest, streams and verifies all blobs into profile-scoped staging, decrypts/authenticates each, validates graph and workspace, calculates post-merge quota against current graph. One final short local transaction merges graph and promotes the verified inventory, with cancellation/version checks at commit. Previous data survives wrong password, corrupt/truncated image, missing file, quota failure and cancellation. Staging persistence is not successful restore; garbage collect incomplete import staging after safe recovery. Never replace an independent workspace. No remote write is implicit in import.
- Account/S3 migration must copy all retained images, upload+download verification (at least digest and authenticated decrypt according to chosen migration gate), bind destination graph+inventory, reread durable graph and required image inventory, check source stability, then activate. Preserve source if any stage fails.

### Migration and execution gates

1. Freeze versioned descriptor, graph/envelope/backup wire formats and independent fixtures first. V1->v2 transformation adds empty attachment lists deterministically, preserves workspace/revision IDs/parents and normalizes both sides before collision comparison. Never manufacture new financial edits simply to migrate serialization. Validate canonical v1 history matches canonical v2 empty-attachment history.
2. Migrate native v2/v3 to a new explicit schema version, preserving profile metadata; Web/Android persisted-state and blob stores must have their own version guards and rollback/reopen cases. Keep source bytes until migration is durable; old application binaries must fail closed on newer state instead of overwriting it.
3. Deliver server readers/capabilities/inventory and storage support before enabling attachment sync in new clients. Existing v1 ledgers remain usable. Explicit v2 enablement has an upgrade warning for other clients; after upgrade, rollback means restore preserved source/pre-upgrade backup to an isolated profile, never downgrade the live remote head or erase new images.
4. Deliver shared crypto/schema/storage; then both transports; then full backup/profile migration; then UI. Do not expose the image button as complete before local restart, encrypted backup and both HTTP/S3 sync are verified end to end.

### Required verification matrix (not run in this planning research)

- Independent AES-GCM interoperability, AAD tamper, ciphertext/descriptor mismatch, nonce/key uniqueness, no KDF on unsupported/oversized envelope, deterministic v1->v2 fixtures.
- Local native v2/v3, OPFS worker and Android IDB compatibility: atomic save, stale edit, crash/reopen, storage-full, profile switch, staged cleanup and graph/blob inventory consistency.
- Two clients HTTP and S3: offline image edits, simultaneous add/remove/delete, graph conflict candidates, CAS contention, missing image, wrong digest, lost PUT response, immutable collision, cancelled session, revoked account, remote quota race and crash reservation recovery.
- Legacy client rejects upgraded graph and does not overwrite it; old server preflight failure; minimum-version downgrade rejection; current SDK generation checks without clobbering unrelated changes.
- Full backup all historical/conflicting/tombstoned refs; large bounded memory; corrupt/truncated/duplicate/missing/extra records; wrong password; disk-full/cancel at final commit; cross-workspace rejection; merged import keeps both existing and imported images.
- Android SAF export/import and Web download/import, large representative fixtures, EXIF removal/orientation, malformed and excessive-pixel images. Real Android verification needs a future separately authorized device/emulator gate; browser screenshots do not establish native file behavior.
- Server deployment backup/restore includes inventory+objects, quota counters reconcile, profile migration copies durable blobs, secrets/image contents absent from logging and renderer list DTOs.

## Caveats / Not Found

- No image pipeline, attachment endpoint, blob quota or full binary backup exists in inspected code. Suggested limits and cryptographic/container contracts are planning decisions requiring implementation review and fixtures, not claims of an existing or audited protocol.
- This is internal repository research; no external references were needed to establish existing capabilities. No live provider, device, remote host or tests were accessed.
- The 512 MiB ceiling requires real mobile memory/storage validation; it cannot be served by today's 12 MiB JSON bridge. Streamed full backup and Android compatibility adapter are mandatory dependencies, not deferred polish.
- Server aggregate user quotas/advertisement, exact frame encoding and commit-time inventory APIs need normative design tables before implementation. The overall plan must select exact values and signatures; this recommendation establishes coherent ownership/order and calls out required extension points.
