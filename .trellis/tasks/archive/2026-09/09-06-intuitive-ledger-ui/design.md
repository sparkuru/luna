# 直观记账 UI 技术设计

## 1. 设计目标与边界

本任务只调整用户可见的信息架构和记账交互，不改变账本、设置、同步或加密协议。Web、Electron 和 Android 共享“最近账单 → 记一笔”的心智模型；桌面端利用弹窗、账单条目和二级菜单展示更多上下文，不把完整专业工作台常驻在主界面。

视频参考提供的是交互启发：账单列表是首页、收入/支出先分流、分类容易选择、统计为次级入口。Luna 使用自己的文案、图标、颜色和布局；当前 frontend spec 的 indigo/green 语义 token 继续有效，不复制参考软件的棕橙主题、城市背景或图标资产。

## 2. 响应式信息架构

### 2.1 共用层级

1. 应用身份（Luna logo）与三横线二级菜单入口
2. 当前工作区、月份/日期等简短信息和显眼的 `page-heading` banner
3. 收入、支出、结余三个摘要卡片
4. 最近账单列表（空状态时直接说明“记第一笔”）
5. 显眼的“记一笔”入口，以及收入/支出分流
6. 二级菜单中的预算、统计、设置、同步、备份和冲突工具

主界面不展示“剩余预算”、完整设置区、分类统计或账本同步表单。平台只能改变弹窗与账单条目的信息密度，不能把同步、路径或加密设置放到首次记账之前。

### 2.2 桌面宽屏

- 主界面仍是单一主路径：banner、三项摘要和宽一些的最近账单列表；账单条目可以展示商户、支付方式等更多上下文，但不新增常驻右侧录入表单。
- “记一笔”打开较宽的交易 dialog；核心字段清晰可见，高级字段在同一 dialog 内渐进展开。
- 三横线按钮打开较宽的二级菜单 dialog；预算编辑、分类统计、隐私/显示设置、语言、配置同步、账本同步/备份和冲突处理都在其中分组展示。
- 筛选器默认为收起状态，只显示一个低强调的“筛选”控制；展开后仍保留完整表单和明确的清除动作。

在现有 `max-width: 1024px`、`768px`、`520px` 响应式断点上迭代，避免为了本次 UI 重构引入无证据的断点体系。桌面端的“更多信息”来自账单条目详情和 dialog 内容，不改变首页主次顺序。

### 2.3 窄屏 / Android

- 默认显示最近账单、三项摘要和一个明显的“记一笔”按钮，不出现横向滚动。
- 点击后进入单主路径录入：类型 → 金额 → 分类 → 保存；日期、备注、商户、支付方式和分类拆分通过“更多信息”展开。
- 三横线菜单占用屏幕并带遮罩；关闭按钮、系统返回键和 Escape（可用时）都能退出，焦点/触控不会落到被遮罩的主界面。
- 保存成功回到账单并聚焦/提示新记录；保存失败留在录入状态，保留用户输入和可重试动作。
- 不新增必须依赖特定键盘或屏幕边缘手势的路径；键盘和触控均需有可见等价操作。

## 3. 共享数据与 API 边界

不新增 renderer 与宿主之间的通用接口。快速录入最终构造现有 `TransactionDraft`，经 `window.lunaLedger.createTransaction()` 或 `updateTransaction()` 提交；金额继续使用字符串 minor units，不能经过浮点 `number`。

快速路径可以先提交一个分类 split，但必须遵守以下规则：

- 已存在的多分类交易继续可读；编辑时显示保护状态，不得用单分类草稿静默覆盖。
- `expectedRevision` 继续传入更新/删除，过期操作显示明确错误并保留用户输入。
- 设置、同步或刷新造成的 snapshot 更新不能替换正在编辑的草稿。
- 保存成功后重新读取当前月 snapshot，统计、预算和列表一起更新。
- 领域校验、SQLite/IndexedDB 事务、冲突和墓碑语义完全复用现有实现。

## 4. 视图状态与交互契约

UI 至少区分：loading、setup/空账单、快速录入 dialog、分类选择 dialog、二级菜单 dialog、保存中、保存成功、保存失败、过期版本、离线/同步待处理和冲突提示。提交按钮在请求期间禁用，不能重复创建记录。

两个 dialog 采用语义化 `dialog` / `showModal()`（或等价的可访问实现），必须有标题、明确关闭动作、Escape 关闭、打开时焦点进入、关闭后焦点还原，并阻止焦点穿透遮罩。交易 dialog 与二级菜单 dialog 互斥；分类选择可作为交易 dialog 内的短流程弹层，关闭后回到分类触发控件。

金额隐私边界保持原有语义但减少首页摘要数量：默认只遮罩首页收入、支出、结余三个摘要金额；每张摘要卡标题旁提供眼睛开关，每个开关只控制对应卡片的金额。切换显示不改变摘要卡片几何尺寸或周围页面流，避免用户在查看金额时产生跳变。交易列表金额、分类统计、二级菜单中的预算编辑值和预算使用/上限保持可见。摘要显示状态不写入配置，reload/重启后按隐私默认值初始化；显示金额的控制必须保持可发现。

所有新增用户可见文字进入 `zh-CN` 与 `en` catalog；分类/快捷标签等用户输入使用 `textContent` 或安全 DOM 构造，不把用户数据拼进 HTML 属性或脚本。

## 5. 可访问性与视觉原则

- 主入口使用明确的可访问名称，例如“记一笔支出”“记一笔收入”；不要只依赖圆形加号图标。三横线按钮也必须有明确的“打开更多/菜单”名称。
- 类型切换、分类选择、更多字段、两个 dialog 和保存状态必须有语义控件、键盘路径、可见 focus 和 `aria-live` 反馈。
- 分类选择器展示已有分类建议，并保留自定义分类输入；选择器关闭或取消不能覆盖用户当前输入。
- 触控目标继续满足至少 44px；窄屏无横向滚动；`prefers-reduced-motion` 下不依赖动画理解状态。
- 空状态说明下一步，不展示需要用户猜测的专业术语。
- 颜色使用 Luna 现有语义 token；收入/支出对比不能只依赖颜色。

## 6. 兼容、验证与回滚

Web 是第一验证宿主：先完成 `npm run web:build` 和正式 Web Playwright，再运行 Electron/Android 集成门禁。浏览器测试不替代真机触控、原生目录/文件选择器或辅助技术人工检查。

主要风险是 renderer 状态重排导致编辑草稿、预算 head、dialog 焦点、同步刷新或多分类保护丢失。实现以小步提交/可回滚边界推进：先保留现有 API 和表单提交函数，再替换视图结构；任一步骤若导致跨层行为变化，回退到上一个已通过 Web/单测的视图版本，不修改领域或持久化层来迁就 UI。
